## Rules that keep the project honest

- **Backtest conventions** (see `core/backtest.py` docstring): target decided at close t,
  filled at open t+1, exposure = target shifted by one bar. Any new rule returns a target
  exposure series. Never index future values.
- `core/` stays pure: no Streamlit imports, no globals, and no network calls except in
  `core/data.py`, which only jobs and scripts use.
- The app is read-only. Pages read `data/` through cached readers and never call yfinance or
  the Claude API. API keys live only in GitHub Actions secrets.
- Thresholds and defaults go in `core/config.py`, not inside functions.
- Every audit fix gets a test. Reported numbers (`docs/PHASE0_FINDINGS.md`) come from scripts;
  don't hand-edit them.
- `notebooks/` is historical and excluded from ruff; don't modify it.
- Before Phase 3, check current Claude model IDs and web-search pricing; the model ID goes in config.

## Project

**SPY Market Lens**

A public Streamlit portfolio app that turns Jason's 2022 moving-average notebook into an honest
SPY backtesting lab, and explains every major SPY dip or spike with sourced, categorised news.
Visitors see price, strategy trades and world events on one interactive timeline, with the
methodology and its assumptions visible. Audience: recruiters, hiring managers and peers viewing
the portfolio, plus Jason as the analyst.

**Core Value:** Every number and every explanation on the page is honest and traceable. Backtests have no
look-ahead and use total-return prices and costs. Event explanations cite sources dated inside
the move's window, or are marked "unexplained". If the app is wrong in public, the portfolio
piece fails.

### Constraints

- **Tech stack**: Python 3.12, pandas/pyarrow, Plotly, Streamlit multipage, pydantic, `anthropic` SDK with web search, pytest + ruff — per spec
- **Hosting**: Streamlit Community Cloud, which has an ephemeral filesystem — all data committed to `data/` by GitHub Actions
- **Security**: Anthropic API key only in GitHub Actions secrets, never in Streamlit Cloud or the repo
- **Budget**: one-off news backfill ≤ ~$25 of Claude API spend; hard caps on episodes per run and searches per request
- **Honesty**: no look-ahead in any signal; every reported figure regenerated by a script, not hand-edited
- **Purity**: `core/` has no Streamlit imports; app never imports `jobs/`
- **Copyright**: own-words summaries, links out, no stored article text

## What NOT to Use
| Avoid | Why | Use Instead |
|-------|-----|--------------|
| **Stooq via `pandas-datareader`** (the current `docs/SPEC.md`/`.planning/PROJECT.md` fallback plan) | Confirmed broken as of 2026: `pandas-datareader` **removed its Stooq reader entirely in v0.11.0** (June 2026) as part of dropping readers that depend on "defunct or broken upstream APIs." Separately, Stooq's own CSV endpoint (`stooq.com/q/d/l/`) now requires an API key obtained via a one-time CAPTCHA flow on their site, and reports describe undocumented daily quotas and temporary blocks. This is a direct conflict with the project's existing "yfinance primary, Stooq fallback" decision and the nightly job's unattended, no-browser requirement. **MEDIUM confidence** — multiple independent 2026 sources agree on the `pandas-datareader` removal and the CAPTCHA/API-key requirement, but I could not independently re-verify Stooq's live current behavior by hitting the endpoint myself in this research pass. | **Recommended fix, flag for Phase 3/automation planning:** (a) obtain a Stooq API key once, manually, and store it as a GitHub Actions secret, then call `stooq.com/q/d/l/?s=spy.us&i=d&apikey=...` directly with `requests` (no `pandas-datareader` needed) — cheap to implement, but re-verify Stooq's current ToS/rate limits before relying on it for a public portfolio project; OR (b) drop the live Stooq fallback entirely and rely on (i) retries/backoff against yfinance, and (ii) the already-planned "last good parquet snapshot stays in `data/`" behavior as the real fallback — a failed nightly refresh simply leaves yesterday's committed data in place, which the spec's own risk table already treats as acceptable. Option (b) is simpler and removes a second scraped, ToS-fragile dependency from a public repo; recommend revisiting the Stooq decision in `PROJECT.md`'s Key Decisions table before Phase 3 (data refresh) is scoped. |
| Reading yfinance's `Adj Close` column as "the adjusted price" without checking `auto_adjust` | Current yfinance default is `auto_adjust=True` (confirmed via official docs for `yfinance.download`), meaning `Close` **itself** is already split/dividend-adjusted and a separate `Adj Close` column may not be present/meaningful depending on version. The existing `data.py` from Phase 0 was presumably built against this already, but anyone touching price-loading code in the app/jobs layer needs to **explicitly pass `auto_adjust=` rather than rely on an assumed default**, since the default has flipped between yfinance versions historically and is exactly the kind of silent behavior change that produces a wrong total-return number on a public page. **MEDIUM confidence** (verified current default via official reference page; version-history framing is community-sourced). | Pin `auto_adjust=True` (or `False`, matching whatever Phase 0's `core/data.py` already assumes) **explicitly** in every `yf.download()`/`Ticker.history()` call in `jobs/refresh_prices.py`, and add a unit test asserting the returned columns match expectations — don't trust the library default silently. |
| `multi_level_index` default assumptions | Current default for `yf.download()` is `multi_level_index=True`, returning a MultiIndex `(Price, Ticker)` column structure **even for a single ticker** in some code paths — a known source of "KeyError: 'Close'"-style bugs when code assumes flat columns. | Pass `multi_level_index=False` explicitly when downloading a single ticker (SPY only, per this project's scope), or always select via `.xs()`/`['Close']` defensively and cover it with a test. |
| Relying on a `git push` from the nightly GitHub Action to "wake" the deployed Streamlit app | **Confirmed changed behavior (verified via official Streamlit docs + community reports): as of April 2025, pushing a commit no longer wakes a sleeping Community Cloud app.** Community Cloud now sleeps after 12 hours of inactivity, and the only documented way to wake it is a visitor clicking "Yes, get this app back up!" in the browser — there is no public API/webhook to force a reboot. This directly affects the spec's framing ("the commit in step four triggers a Streamlit Cloud redeploy, so the public app is never more than one trading day stale") — that framing is only true for an **already-awake** app; a sleeping app stays asleep (showing stale data) until a human visits it, regardless of how fresh the committed data is. **HIGH confidence** on the sleep-after-12h and manual-wake-only facts (official docs + Streamlit discourse); this matches the project's own risk table, which already (correctly) calls this "Acceptable for a portfolio" — this entry is here so the *automation* design doesn't silently assume otherwise. | Nothing to "fix" — just design the nightly job's "trigger redeploy" step as a no-op/best-effort for an awake app (an ordinary `git commit` + `git push` is sufficient; Streamlit Cloud auto-redeploys any **running** app near-instantly on push) and keep the README's "may take a moment to wake" disclaimer for a cold app, exactly as the spec's risk table proposes. Do not build a custom keep-alive pinger — it burns Actions minutes for a portfolio piece where "may be asleep" is an acceptable, disclosed state. |
| Treating `web_search_20250305` as "the" tool version without checking for newer variants | Anthropic has shipped two newer web-search tool versions since: `web_search_20260209` (adds dynamic filtering, which runs search through code execution and changes default `allowed_callers`) and `web_search_20260318` (adds `response_inclusion` control). These aren't required for this project's modest, one-search-per-episode use case, but **picking a tool version string and recording it in `jobs/enrich_events.py`'s config (plus the stored `prompt_version` field already in the spec's data model) matters for reproducibility** of a public portfolio artifact. **HIGH confidence** (official docs enumerate exactly these three versions and their capability deltas). | Use the plain `web_search_20250305` type string for this project — the episode-explanation task is single-topic, bounded by `max_uses`, and doesn't need dynamic filtering's extra code-execution machinery or `response_inclusion`'s token-trimming (episodes are small; a handful of search results per call is not a token-cost problem at this project's scale). Record the exact tool-type string alongside `model` and `prompt_version` in each stored event record, per the spec's own data model — this is "which tool version produced this citation" provenance, free to add now. |

## Stack Patterns by Variant
- Drop `pandas-datareader` from consideration entirely (it's not even in `pyproject.toml` today, so this is a non-change to dependencies).
- Either add a thin `requests`-based Stooq client keyed to a GitHub Actions secret API key, or simplify to "yfinance + retries + last-good-snapshot" and update the Key Decisions table accordingly.
